# Architecture

Herdr Git Mods is one Herdr mod, `git`. The source is TypeScript in `src/`. Bun bundles it into one ES module, `mods/git/main.js`, which Herdr loads and which default-exports a `View`. Herdr runs mods in QuickJS, with no TypeScript, Bun, or Node APIs, so the bundle is committed and nothing in `src/` may use those APIs at run time.

## Pane presentation

Git opens as a full-height mod pane at the active tab's far right. Installation and use must not create, clone, or modify a Herdr layout file or a shipped mod.

- `keys.json` binds ⌘G to `mod.open:git`. The overlay copy is a frameless 2×2 launcher that draws nothing, toggles the tab's Git pane, and closes itself.
- `pane-target.ts` reads the tab's current root from herdr-core's `doc.get` through `hc connect`. It never writes the core document. Unix uses `sh`; Windows uses PowerShell. Remote lookups name the space's machine and qualify the returned node id.
- `pane.ts` splits that root with `pane.split {direction: "right", mod: "git"}`. Keep the entire existing tree as the left child: never split a focused or rightmost leaf as a fallback. If the root cannot be read, report the failure without changing panes.
- Opening focuses Git. Its width comes from the native split; resizing and zooming use Herdr's pane controls. Existing panes keep their arrangement and relative sizes in the remaining space.
- A second ⌘G closes the existing Git pane in the active tab, even after it has been moved. `git.close` closes the pane, not the tab or a terminal.
- Repository selection follows terminal focus within the pane's tab. Focusing Git retains its source terminal's live folder and machine. Explicit project/worktree selections stay pinned until the Workspaces `Current` row is chosen; `Current` always shows the followed terminal folder. Switching tabs retains each pane's own repository rather than following another tab's focus.
- Each Git view owns one `RepositoryContext` and passes it to its panels. Never store repository selection in module-level mutable state: multiple pane and launcher copies share loaded modules.

## Source layout

```text
src/
├── main.ts       View entry: implements Services; owns repository context, status, mutation queue, shell, tabs and dialog host
├── git/          Git reads, parsing and operations; no host imports
├── herdr-builtins.d.ts   Types for native APIs absent from the Herdr declarations
├── ui/           Shell, tabs, dialogs, theme and widgets (one module per TUI screen)
│   ├── theme.ts, icons.ts, widgets.ts, shell.ts, overlay.ts   Shared foundation
│   ├── changes.ts + changes/     Changes tab
│   ├── graph.ts + graph/         Graph tab
│   ├── explorer.ts + explorer/   Files tab
│   ├── workspaces.ts + workspaces/   Workspaces box shared by the tabs
│   ├── commands.ts + commands/   Command palette and every operation dialog
│   ├── settings.ts               Settings tab
│   └── code-view.ts, syntax.ts   Code and diff rendering shared by the tabs
├── runtime/      Pane placement, repository selection, Herdr context and release verification
└── version.ts    Version and release bundle format shared with the build
mods/git/         Installable manifest, icon and generated bundle
tests/            Real-Git and pane-context regression tests
scripts/          Build, checks and local installation
```

The UI modules follow herdr-git's `src/ui/` modules of the same name, so a TUI behavior can be found in the matching file. [DESIGN.md](DESIGN.md) describes the screen.

The repository root follows the layout Herdr expects for a shared mod: `RECIPE.md`, `preview.png`, and `keys.json` next to `mods/`, and no `layouts/` folder. [research/herdr-mods-research.md](research/herdr-mods-research.md) explains why.

Herdr Git Mods is developed as a mod. Developing or requiring a custom Herdr layout is outside the project's scope.

## Build

`scripts/build.ts` bundles `src/main.ts` as an ES module and leaves `gpui-kit`, `gpui-base`, and `herdr` as imports, because Herdr provides them. Static files such as `mod.json` and icons live in `mods/git/` directly. `bun run build:check` fails when the committed `main.js` differs from a fresh build.

Herdr's type declarations are generated by the installed app and must not be committed. `bun run types` copies `herdr.d.ts` and `gpui-kit.d.ts` from `~/.config/herdr-app` into the ignored `.herdr-types/`, and `tsconfig.json` resolves `herdr` there.

"Foundation" is `theme.ts`, `icons.ts`, `widgets.ts`, `shell.ts` and `overlay.ts`. Only the dependencies shown above are allowed.

- The release workflow uploads the tagged `mods/git/main.js` as the `main.js` asset. The build maps `node:crypto` to Herdr’s native `crypto` module. The updater verifies the GitHub SHA-256 digest and version header, then uses Herdr's compare-and-replace file API. Keep the bundle within the host's 1 MiB text read limit. Record the background check time before the request so a mod reload cannot immediately retrigger it.
- `shell.ts` defines the contract between the view and its tabs: `TabView`, `Services`, `CommandHandler` and `RefreshScope`. `main.ts` implements `Services`, `commands.ts` implements `CommandHandler`, and each tab module implements `TabView`. `overlay.ts` hosts the single active dialog drawn over the whole view.
- Tabs reach each other only through `Services` (`setTab`, `revealCommit`, `openCommitDiff`, `commands()`) or the tab methods `commands.ts` calls. A tab never imports another tab's module, except `commands.ts` for the operations it routes.
- `context.ts` reads Herdr's focused terminal and machine. `main.ts` uses it to bind every asynchronous read and mutation.
- `repository.ts` imports nothing. It receives a function that runs Git, so Herdr passes `exec` and the tests pass real Git. Every module in `git/` receives the same runner and hides command arguments and exit handling from the view.
- `history.ts` anchors pagination to immutable revision IDs. `workflows.ts` models each operation with its exact Git arguments and the TUI's guards, and reviewed operations snapshot the repository and refuse to run if it changed after review.
- `history-maintenance.ts` prepares Git's split commit-graph before Graph's first read in each repository context. The asynchronous task uses a repository/machine-pinned runner with a five-minute timeout; tabs remain usable and Graph shows `Preparing history`. It honors `core.commitGraph=false`, `maintenance.commit-graph.auto=0`, shallow repositories and replacement refs. Git itself refuses graph writes with grafts. It changes neither refs nor configuration, runs no GC/repack, and starts no daemon. A failure is a visible nonfatal warning, not a reason to hide history. Completed preparation means the Git command completed, not proof that Git wrote an index.
- Graph retains its immutable revision cursor and existing date/topological ordering. Each cursor keeps the original refs and removes redundant ancestor tips with `merge-base --independent` for traversal, preserving every reachable commit, including disconnected history. Subsequent pages reuse those frozen traversal tips even when refs move. Equal-timestamp ties may differ from the old redundant-tip traversal; pagination remains deterministic. Preparation time is separate from query time; the full-history performance gate measures both. There is no Rust helper or persistent subprocess.
- Each repository refresh supplies one root-relative porcelain status snapshot to Changes and to matching Workspaces reads. Both use the same working-summary implementation. A per-session runner shares only identical in-flight numstat requests; settled results are discarded, so unchanged porcelain never conceals changed line counts. Workspace refreshes coalesce while an inspection is running and apply results only to the same repository, machine and followed location. Mutation runners remain independent.
- `code-view.ts` renders source and diffs for Changes, Graph and Files. Each tab releases its code views on close.
- `tsconfig.json` loads no Bun or browser types for `src/`. The host's `window` declaration is GPUI's native drawing surface. Tests and scripts use `tests/tsconfig.json`, which adds Bun's types.

## Runtime rules

These follow from how Herdr runs mods. `~/.config/herdr-app/AGENTS.md` and the `.d.ts` files next to it are the source of truth for the installed version.

- Never keep a `cx` for later. Use the one each callback receives. Create `InputState` and focus handles in constructors or handlers, never in `render`.
- `h_flex` centres its children vertically. Give a full-height pane or scrolling area inside one `items_stretch()` (or `h_full()`), or it measures its content height and stays one row tall.
- Lists draw only their visible rows with `ListViewport` from `widgets.ts` (or a tab's own row viewport), which owns the scroll offset so wheel, scrollbar, keyboard and pointer hit testing agree.
- Run Git and file reads through `exec`, `readTextFile`, and `watchFolder` inside `cx.spawn`. Render from in-memory state only.
- Pass `on: space.machine` to `exec` so remote spaces run Git on their own machine. `watchFolder` works only on this machine; refresh remote repositories with a timer.
- Before applying an asynchronous result, check that it belongs to the repository still in focus. Discard results that a newer request superseded.
- Run mutations through `Services.mutate`: pinned to their starting root and machine, serialized, followed by a refresh. Surface failures without automatically repeating a mutation.
- Destructive operations (discard, reset, branch delete, force push, rebase) open a confirmation first and revalidate before running.
- Key handlers ignore Alt/Ctrl/Cmd chords and never stop typed characters from text inputs, so shell shortcuts reach `shell.ts`.
- Herdr reloads every copy of the mod when a file changes and has already run the module's top level. Keep side effects out of the top level.

## Adding features

- Add behavior to the module responsible for that data or operation. Create a sibling module when the behavior falls outside every existing module's responsibility.
- A feature may stay in one file.
- Extract shared code only when existing callers need the same behavior. Code that looks alike does not need an abstraction.
- Keep logic that tests must reach out of `main.ts`, in modules that do not import Herdr.
- Work within these boundaries where you can. If a feature needs a new module or dependency, update this document in the same change and explain why in the pull request.
